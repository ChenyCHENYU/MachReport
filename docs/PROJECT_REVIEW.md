# 产品评审与验收范围

当前主线是可复用报表 SDK：模板与数据生成统一 RenderPlan，供预览、编辑、打印与输出复用。常规页面只传报表 ID 和参数，模板、字段、请求与存储适配集中注册。复杂度继续收在包内，业务权限、数据口径和数据库事务由宿主负责。

复杂模板验收使用明确标识的合成数据，包含前导零、零/空值、长文本、条件样式、分组汇总、高精度字符串和三层合并标题。六张业务原表是接入样本；引擎的支持范围和验证不限于某个工厂或接口。

可运行的[复杂报表体验页](../examples/minimal/product.html)展示完整宽表、A3/A4选配、类型编辑、原生设置、列目录及输出诊断。[Java→Node参考](../examples/server-java-node/README.md)展示后端协议与受控执行。详细测试环境与本轮实测数字以[质量说明](./QUALITY.md)为准。

## 保持明确的能力边界

- 完整模板分页仍构造完整计划；窗口化约束DOM数量，流式数据Excel使用独立Node出口。实际字体、长单元格、列数与资源都会影响性能，不能用单一行数推导无限容量。
- Excel导入转换单元格模型与已保存值。完整公式计算、宏、透视编辑和自由拖拽工作簿设计器，需要明确需求与独立适配；诊断/strict不会自动补齐不支持的内容。
- PDF、Canvas、DOM和XLSX有不同的排版模型，真实文件回读、字体与阅读器验收仍然必要。Word出口为兼容HTML的.doc。
- Node运行时与参考HTTP服务不代替认证、租户隔离或数据库事务。Java继续负责业务规则，可复用JSON契约并调用同一Node引擎。
- 默认队列为进程内有界队列。多实例的持久任务、业务重试和审计平台按宿主既有设施适配，不引入通用插件核心。

## 后续维护方式

新增复杂模板先明确数据契约、版式与输出目标，再加入可重现fixture、结构/值断言和必要的视觉用例。修复应由共用模型、几何或生命周期承担，避免在使用页面堆补丁。持续使用相同预算与零重试门禁，记录真实兼容组合；工作流配置或测试数量本身不等于未执行环境已经验收。
